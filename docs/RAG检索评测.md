# 拾语 RAG 检索评测

本评测使用合成中文长期记忆 fixture，比较 PC/服务端结构化记忆链路的
FTS5/词法基线和 FTS5+BGE 语义检索。它衡量记忆候选是否被检索到，不代表最终回答
正确率，也不代表真实用户聊天分布。

可复现入口：

```powershell
python scripts/evaluate_rag_retrieval.py `
  --embedding-model "outputs/models/bge-small-zh-v1.5"
```

跟踪文件：

- `evaluation/rag/retrieval_v1.json`
- `scripts/evaluate_rag_retrieval.py`
- `outputs/rag-evaluation-v1/report.md`（生成目录不进入 Git）

`evaluation/rag/retrieval_v1.json` 是固定输入。脚本默认只读取，不会在每次运行时
覆盖；确实需要从脚本内常量重建时才使用 `--refresh-fixture`。

本次实测环境为 Windows、项目的 `qwen3-im-chat` Conda 环境；BGE worker 使用 CPU
推理，模型目录为 `outputs/models/bge-small-zh-v1.5`。

## Fixture

- 记忆条数：60
- 查询数：68
- 可回答问题：60
- 无答案问题：8
- 查询类别：词面重合、同义改写、易混干扰、无答案

## 结论

- BGE 对同义改写有明显价值：Recall@5 从 `0.533` 提升到 `0.967–1.000`。
- 生产代码当前使用的 `0.30` 语义阈值会召回无关问题，本 fixture 上无答案误召回为 `1.000`。
- `0.40` 是本 fixture 的最佳平衡点：Recall@5 `1.000`，无答案误召回 `0.000`，热查询平均延迟约 `21.4 ms`。
- 首次 BGE 推理约 `6.3 s`，属于模型加载冷启动；实际服务应预热模型或异步初始化。
- 当前尚未评测最终的 LLM 回答正确率、引用证据正确率、事实幻觉率或人工偏好。

## 适用范围

- 本次实测的是 PC/服务端 `CandidateStore`：FTS5、词法排序和
  `bge-small-zh-v1.5`。
- Android 云端版使用 FTS4、独立的 Qwen3-Embedding-0.6B ONNX INT8 和 Kotlin
  侧融合排序，不能把本页数字直接当成 Android 端实测结果。
- Android 目前只有 JVM 单元测试和 App 内“检测语义检索”，还没有在同一套标准 IR
  fixture 上运行量化评测。后续需要在真机或 Android 测试环境补齐同口径指标。

## 后续

1. 在 PC 探测链路中先做阈值 `0.40` 的离线 A/B，不直接改动生产默认值。
2. 为 Android 的 Qwen embedding 建立同口径 fixture 和指标输出。
3. 用真实脱敏聊天构建第二套固定集，避免只依赖合成数据。
4. 增加端到端回答事实正确率、证据支持率和无关记忆干扰率。
