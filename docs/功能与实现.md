# 功能与实现

拾语不是单一聊天框，而是把角色档案、世界书、长期记忆、关系状态、当前场景和
模型回复组织成一条连续链路。本文说明各项功能的行为、实现方式和平台差异。

## 1. 角色档案构建

角色卡是角色行为的基础数据结构，包含：

- 姓名、一句话介绍、身份简介和背景。
- 性格、说话方式、与用户的关系、互动边界。
- 中文外貌、英文生图提示词、主动开场白。
- 当前情境、人物动机、稳定目标和示例对话。
- 角色类型、时代、知识截止、允许/禁止知识和禁止词。
- 固定事实、世界书、模型来源与生成参数。

创建角色时，模型一次返回结构化 JSON。应用随后执行字段规范化和校验：

- `description`、`personality`、`speech_style`、`relationship` 有最低完整度要求。
- 外貌必须足够具体；英文提示词必须以 `1girl`、`1boy` 或 `1person` 等主体标签
  开头，并包含年龄、发型、眼睛、服装和简单构图。
- 世界书条目必须带触发关键词、内容、优先级和启用状态；新角色默认要求生成至少 4 条，
  请求模型覆盖世界规则或时代背景、关键地点、组织或势力、关键历史或秘密、角色知识边界。
- 世界书支持分类与 `constant` 常驻规则。常驻条目忽略关键词和冷却，每轮作为世界背景
  参与预算；普通条目仍需关键词命中。编辑页可以直接切换启用和常驻状态。
- 模型生成的具体设定先标记为 `proposal`，不会自动升级为作者确认事实。
- 编辑页可以逐条查看固定事实并切换“待确认提案 / 已生效”；只有已生效条目进入
  运行时 Prompt。
- 缺失视觉或世界书材料时，只发起一次定向补齐请求，不重新生成整张角色卡。

角色卡保存后由审核页展示，作者可以修改全部字段。固定事实、世界书、知识边界和
开场消息都来自这份档案，而不是每轮让模型重新决定角色身份。

主要实现：

- PC：[character_cards.py](../src/character_cards.py)、[backend.py](../src/backend.py)
- Android：[CharacterGenerationPolicy.kt](../android/app/src/main/java/com/shiyu/chat/data/CharacterGenerationPolicy.kt)、
  [ChatRepository.kt](../android/app/src/main/java/com/shiyu/chat/data/ChatRepository.kt)

## 2. 对话上下文与 Prompt 组装

普通角色每轮采用类似 Prompt Manager 的分区组装，而不是一长段不可解释的拼接：

1. 角色固定身份、性格、说话方式和与用户的关系。
2. 输入安全边界，明确用户文字、图片文字和记忆都是低权限数据。
3. 普通回复的节奏要求，例如先回应当前内容、避免连续追问。
4. 当前场景和本轮即时反应。
5. 关键词命中的世界书条目。
6. 角色时代、知识范围和禁止词约束。
7. 与本轮相关的结构化记忆和近期历史。
8. 确定性的交流策略，例如倾听、庆祝、继续话题、讨论或结束聊天。

System Prompt 分为角色原则、行为与用户控制、正式角色档案、作者确认事实、认知边界、
场景、世界设定 Lore、剧情摘要、聊天长期记忆、事件、旧摘录、交流策略和即时情绪等
独立区块。必需区块始终保留；可选区块按优先级进入约 9,000 字符的系统分区预算。
被预算排除的区块会写入本机 Turn Trace，并可在只读 Prompt Inspector 中查看。
Prompt Inspector 同时记录本轮实际命中的世界设定标题，便于区分“模型自行编造世界规则”
和“Lore 条目正常触发”。

行为原则明确要求角色以本人身份说话和行动，允许表达自己的判断、提出安排或做低风险
行动，但不要求每轮行动，也不得替用户决定台词、心理和重大行为。事实优先级明确为：
现实安全与用户边界、作者确认角色事实、当前用户更正、已核实记忆、世界设定、临时
表达策略。

世界书作为 `Lore` 域单独标注和组装，只由最近对话与当前消息触发，不直接扫描长期
记忆来生成世界设定。长期记忆则作为 `聊天长期记忆` 域单独召回，两者共享上下文预算，
但来源和权限不混用。

世界书不会整本常驻。应用扫描最近对话和当前消息，只放入命中关键词、按优先级
排序的少量条目。长期记忆也先经过“本轮是否真的需要检索”的判断；短寒暄、表情
和低信息消息通常不触发记忆检索。

宋知意和裴既明使用与 LoRA 训练一致的精简固定 Prompt。这两个角色不追加普通
角色卡、世界书、长期记忆或动态状态区块，以避免训练时短提示与运行时长提示之间
出现分布差异。

PC 还会在模型输入中移除跨轮高度重复的旧角色句子，减少小模型复读；原始聊天记录
不会被修改。切换到另一个 Provider 时，会明确告诉模型上一条消息只是历史，不是
待续写草稿。

## 3. 结构化长期记忆

每次正常回复保存后，后台任务从最近一批原始消息中提取候选记忆。提取结果不是
直接写入数据库，而是经过三层处理：

1. **逐字证据校验**：候选必须包含来源消息 ID、说话人和原文连续片段；用户事实
   不能由角色消息证明，角色自述也不能证明用户事实。
2. **语义审核**：判断证据是否真的支持候选，并区分事实、偏好、计划、假设、观点、
   共同事件和角色即兴自述。
3. **保守操作策略**：执行新增、合并、更正、争议或忽略。旧值保留为历史版本；
   删除会生成墓碑，同一旧原文不能悄悄恢复已删除事实。

记忆会保留来源权限和认知状态。例如：

- `用户明确说过`、`双方共同经历`和`角色第一人称自述`具有不同权限。
- 计划、假设、玩笑、转述和否定不能被写成已经发生的确定事实。
- 角色即兴自述记为 `role_claim`，不会自动覆盖作者角色卡。

检索前，应用先判断本轮是否需要记忆。出现“上次、后来怎么样了、我之前、更正、
不要记”等线索时会检索；普通较长话题、问题和中短句也会检索，只有“哈哈、晚安、
在吗”等高信息量很低的消息跳过。明确指代、更正和不超过 60 字的短消息会使用最近
发言扩写查询，减少“那次旅行”和“去厦门玩”这类说法没有逐字重合时的漏召回。

PC 检索使用 SQLite FTS5、确定性词法匹配和可选本地
`BAAI/bge-small-zh-v1.5` 向量召回。BGE 缺失时自动回退。Android 默认使用 Room
数据库、FTS4 和词法排序，也可由用户按需下载或导入 Qwen3 embedding 模型。
结构化事实、摘要和历史摘录共享上下文预算；
每个角色还有独立的后台记忆 Token 预算。

结构化记忆少于 500 条时直接对当前角色记录排序。超过 500 条后，先通过 FTS、
词法、近期记录、边界和少量核心资料生成候选集合；PC 还会加入已缓存 BGE 向量命中，
再对缩小后的集合进行综合重排。

Android 的上下文不是“关键词命中才给记忆”。每轮会保留最多 2 条核心用户资料、
2 条人工钉住事实和 3 条近期事实，再把本轮真正相关的事实、旧原话和未完成事件叠加
进去。这样即使当前说法没有逐字命中旧记录，角色仍有连续资料可承接；同时用数量上限
避免把整个记忆库灌进 Prompt。最近未完成的计划或约定在没有直接命中时也会作为一条
剧情线索保留，但 Prompt 明确要求只在当前话题相关时自然承接。

OpenCode Go 的记忆提取和语义审核不使用 `response_format=json_object`，因为其
上游网关可能拒绝该参数；JSON 结构由系统提示约束并在本地解析、校验。升级还会重新
排队此前因该参数或截断 JSON 失败的记忆任务，用户不需要清空角色或聊天记录。

云端新角色还有一层滚动剧情摘要。最近 30 条消息保留原文，不参与压缩；当窗口外
积累了至少 24 条尚未摘要的消息时，后台模型把它们与旧摘要合并，最多生成 8 条、
900 字以内的剧情摘要。摘要保存覆盖的消息范围和来源 ID，每轮固定注入 Prompt，
用于承接最近原文窗口之外的共同经历、计划、关系变化和未完成事件。摘要随分支快照
保存和恢复，重置角色或分支切换时不会串入另一条剧情线。

召回和重排使用多个独立信号：FTS4、中文词面、常见近义表达、近期顺序、重要度、
来源可信度、人工钉住、事件进展和记忆时效。使用次数只用于调试统计，不提高排序；
相关性结果不足时会用核心资料
和近期事实保底；陈旧计划和假设会随时间降低权重，但不会被静默删除。完全重复的事实
会在后台合并并把旧记录标记为已替代。

Android 另外提供可选的 `Qwen3-Embedding-0.6B-ONNX` INT8 语义记忆。模型不进入 APK，
用户可以在设置中下载约 596 MiB 的模型包，或导入包含 ONNX、tokenizer 和 config 的
ZIP。应用校验文件大小和 SHA-256，使用 Qwen byte-level BPE、查询 instruction、
最后 token pooling 和 L2 normalization，生成 1024 维向量并保存到 Room 的
`memory_embeddings` 表。

每轮只对已经召回的结构化记忆候选做精确 cosine 打分，再与 FTS4、词面和生命周期信号
融合。模型未安装、加载失败或索引尚未完成时自动回退到原有 FTS4 路径。删除模型会同时
删除对应向量；切换分支或删除角色会清理分支范围的向量索引，再按需要重建。

## 4. 事件记忆与未完成事项

计划、约定和共同事件会从已经验证的记忆中形成一条小型事件链。事件记录包含主题、
摘要、参与者、状态、来源消息和时间线。

- `open` 表示仍待发生或需要继续跟进。
- `completed` 表示已经有完成证据。
- `cancelled` 表示用户明确取消、放弃或无法继续。
- 后续消息会追加到同一主题的时间线，而不是创建多个互不相关的事件。
- 用户问“后来呢、上次那件事、进展怎么样”时，只选择相关的未完成事件承接。
- 历史问题可以检索已完成或已取消事件；事实更正不会被直接视为完成。

事件记忆不额外调用一次模型，而是从已验证记忆派生，降低成本和虚构风险。

主要实现：

- Android：[MemoryEventPolicy.kt](../android/app/src/main/java/com/shiyu/chat/data/MemoryEventPolicy.kt)
- PC：结构化记忆事件记录与上下文检索位于 [structured_memory.py](../src/structured_memory.py)

## 5. 内部心情与关系状态（产品聊天不注入）

内部状态包含：

- 心情：效价、唤醒度和自然语言标签。
- 关系：熟悉度、信任度、温暖度、关系阶段。
- 用户明确设置的互动边界。

模型只能提出“发生了什么事件”和很小的变化建议。数值范围、单次变化上限、自然
衰减和关系阶段全部由确定性代码管理：

- 心情会向平静基线衰减；温暖度使用更长半衰期。
- 冲突可以暂时标记关系紧张，修复会进入关系修复中。
- “好感度、你必须完全信任我、强制成为恋人”等胁迫表达不会被当作状态更新依据。
- 状态变化需要证据，并记录变更前后值和去重键。

经过同一角色、同一 Prompt 和同一场景的 OpenCode 多轮对比，产品普通聊天最终
只保留 `off` 行为：不把心情、熟悉度、信任度、温暖度或关系阶段写入 Prompt。
`lightweight` 没有稳定优于 `off`，`legacy` 也没有改善计划回忆、冲突修复或边界
遵守。旧表和历史数值仍保留用于调试，但不再是产品聊天条件。

用户明确边界不属于情绪状态，仍会独立进入 Prompt。当前轮的好消息、压力、冲突和
修复会影响即时语气，但不会被当成长期关系数值强行续写。

主要实现：

- PC：[internal_state.py](../src/internal_state.py)
- Android：[InternalStatePolicy.kt](../android/app/src/main/java/com/shiyu/chat/data/InternalStatePolicy.kt)

## 6. 当前回合情绪与场景状态

当前回合情绪是临时表达倾向，不直接修改长期关系。例如用户分享好消息、压力、冲突、
道歉或明确边界时，本轮回复会调整语气、幽默程度和主动性；长期状态仍由后台证据
审核决定是否变化。

场景状态只在用户明确建立或退出剧情时改变。日常聊天不会因为一句“今天好累”就
自动声称双方正在某个地点。沉浸式场景会记录地点、当前活动、参与者和来源消息，
并只承接已经发生的剧情。

主要实现：

- [CurrentTurnAffectPolicy.kt](../android/app/src/main/java/com/shiyu/chat/data/CurrentTurnAffectPolicy.kt)
- [SceneStatePolicy.kt](../android/app/src/main/java/com/shiyu/chat/data/SceneStatePolicy.kt)
- PC 对应策略在 [experience_policy.py](../src/experience_policy.py)

## 7. 语音与图片

PC 完整环境支持：

- Whisper 语音识别。
- CosyVoice 2、GPT-SoVITS 和 MeloTTS 角色语音。
- Diffusers + MeinaMix V12 本地角色立绘。

Android 支持：

- sherpa-onnx 本地语音识别。
- VITS zh-ll 本地角色朗读，按角色保存音色。
- 千问图片 API 或导入 Local Dream SD1.5/QNN 模型。
- 本地生成先保留 1:1 原图，再由用户选择 9:16 聊天背景，并从背景中裁剪
  1:1 头像。

模型权重不随 APK 或 Git 仓库分发，用户需要按应用内说明下载或导入。

## 8. 平台差异

| 能力 | PC 网页完整环境 | Android |
|---|---|---|
| 云端模型 | OpenCode Go、DeepSeek 官方 | OpenCode Go、DeepSeek 官方 |
| 本地语言模型 | Qwen / LoRA | MNN Q8 |
| 记忆检索 | FTS5 + 词法 + 可选 BGE | FTS4 + 词法 + 可选 Qwen3 embedding |
| 本地生图 | Diffusers / MeinaMix | Local Dream QNN |
| 语音 | Whisper、CosyVoice 2、GPT-SoVITS、MeloTTS | sherpa-onnx、VITS |
| 数据同步 | 无 | 无 |

PC 和 Android 都使用角色卡、世界书和结构化记忆；历史内部状态表仍保留但不在产品
聊天中注入。数据库与模型运行库分别实现，不会自动跨设备同步。
