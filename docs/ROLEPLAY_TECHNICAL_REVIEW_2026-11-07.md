# 拾语角色扮演技术设计评审

更新日期：2026-11-07
适用范围：PC 网页端、Windows EXE 基础版、Android 客户端
目标：说明拾语如何让大模型稳定扮演角色、目前做到哪一步、主要技术缺口以及可继续优化的方向。

## 1. 结论先行

拾语不是只把一段“你是某某角色”的人设塞进 Prompt。当前系统由以下几层共同工作：

1. **角色卡**规定角色是谁、如何说话、与用户处于什么关系，以及知识边界。
2. **世界书**在对话命中地点、人物、事件等关键词时补充局部设定。
3. **最近对话**提供当前话题、措辞习惯和正在进行的事件。
4. **长期记忆**保存用户事实、角色经历、共同事件、偏好、计划和边界。
5. **内部状态**保存角色的心情、熟悉度、信任、温暖和关系阶段。
6. **提示词编排**按优先级把这些信息组装成模型输入。
7. **输出守卫**处理时代越界、禁止知识、重复回答和明显的系统指令注入。
8. **后台异步处理**负责记忆抽取、事实校正、状态更新和摘要，不阻塞当前回复。

当前产品已经达到“可持续聊天、可创建角色、可积累记忆、可在 PC 和 Android 运行”的阶段，但还不是完整的角色智能体。它缺少场景状态机、角色的自主目标和计划、事件级长期叙事、在线人格一致性审核以及大规模真实长对话评测。

最重要的技术判断是：

- **角色身份和语言风格**已经能通过角色卡、固定精简提示词和 LoRA 得到较好控制。
- **短期上下文**已经可用，但长对话仍会丢失细节。
- **结构化记忆**的工程完整度较高，但真实模型上的抽取准确率、冲突处理和多跳语义检索仍不够。
- **内部状态**已经能影响下一轮表达，但状态维度、变化阈值和衰减模型仍偏简化。
- **真实感**目前主要来自语言生成；角色的主动意愿、行动后果、长期成长和场景连续性仍然较弱。
- Qwen3-1.7B LoRA 适合做固定角色的离线 Demo 和风格实验，尚不适合承担通用高质量角色扮演。

## 2. 一次聊天请求的完整链路

用户发出消息后，系统大致执行以下步骤：

1. 读取当前角色的角色卡。
2. 读取该角色最近的原始聊天。
3. 读取该角色当前有效的结构化记忆和早期原话摘录。
4. 根据当前问题计算记忆检索文本。PC 在“刚才那个”“上次那件事”等指代出现时，会合并最近两条用户消息作为检索查询。
5. 用角色 ID 做隔离，只检索当前角色的记忆。
6. 把结构化事实、早期原话和会话摘要放进同一预算中统一排序。
7. 命中世界书条目，加入角色所处地点、职业、关系或关键经历等局部设定。
8. 生成内部状态的自然语言描述。
9. 按“角色与规则 → 世界书 → 知识边界 → 长期记忆 → 内部状态 → 最近对话 → 当前用户消息”的顺序组装 Prompt。
10. 调用云端 DeepSeek/OpenCode，或调用手机本地 MNN 模型生成流式回答。
11. 检查回答是否包含禁止词；必要时替换为保底回答。
12. 保存用户消息、角色回答、Prompt 版本哈希、记忆 ID、检索分数、状态快照、Token 和延迟等信息。
13. 回复完成后创建后台任务，异步抽取记忆并评估是否更新内部状态。

PC 与 Android 共用同一设计思想，但实现细节不同：

| 能力 | PC 网页端 | Android |
|---|---|---|
| 角色卡 | 完整规范，支持固定事实、示例对话、世界书等 | 简化角色卡，保留运行时必需字段 |
| 文本检索 | SQLite FTS5 | SQLite/Room FTS4 |
| 语义检索 | 可选本地 BGE-small-zh-v1.5 | 预留接口，默认不打包语义权重 |
| 上下文裁剪 | 按真实聊天模板和模型预算裁剪完整问答轮次 | 最多读取最近约 24 条，并按粗略 Token 估算控制 |
| 结构化记忆 | 完整后台任务、语义审核、版本和证据链 | 同步主要规则，适合端侧资源限制 |
| 内部状态 | 完整 | 同步主要规则 |
| 本地模型 | Qwen/LoRA 实验链路 | MNN Qwen3-1.7B，可安装专用权重 |

## 3. 角色档案如何构建

### 3.1 角色卡的主要字段

完整角色卡包括：

- `name`：角色姓名。
- `tagline`：一句话标签。
- `description`：身份、背景和当前处境。
- `public_intro`：首次见面时给用户看的第三人称介绍。
- `background`：作者提供的背景材料。
- `personality`：性格、行为方式和矛盾点。
- `speech_style`：语言节奏、用词、句子长度和动作表达习惯。
- `relationship`：角色与用户的关系、距离和边界。
- `appearance`：中文外貌描述。
- `appearance_prompt`：本地生图使用的英文视觉提示词。
- `greeting`：保存角色后主动发送的第一条消息。
- `boundaries`：现实信息、隐私、拒绝和关系边界。
- `knowledge_boundary`：时代、世界范围、知识截止、允许与禁止知道的内容。
- `fixed_facts`：由作者确认、不可被聊天内容随意改写的固定事实。
- `worldbook`：按关键词触发的局部资料。
- `example_dialogue`：语气和接话方式的示例。

Android 当前保存的是压缩后的运行字段，主要包含姓名、标签、简介、初次见面介绍、性格、说话方式、关系、外貌、生图提示词、开场白、知识边界和世界书。它没有完整保存 PC 版的全部固定事实和示例对话字段。

### 3.2 角色卡生成流程

角色创建采用“生成 → 校验 → 定向补齐 → 人工审核”的流程：

1. 用户只输入角色名、身份或一段创作灵感。
2. 大模型输出结构化 JSON 角色草稿。
3. 程序检查长度、类型和完整性，重点检查：
   - 简介是否足够具体；
   - 性格是否有行为描述；
   - 说话方式是否具有可执行性；
   - 与用户的关系和边界是否明确；
   - 外貌是否覆盖性别、年龄感、脸型、发型、服装和气质；
   - 英文生图提示词是否独立生成，是否超过 CLIP 预算；
   - 世界书是否至少有两条可用内容。
4. 字段缺失时，第二次请求只补缺失材料，而不是重新生成整张卡。
5. 生成后进入档案审核页；用户可以修改后再保存。
6. 角色保存后才有开场消息，不把模型草稿直接当成不可修改的正式设定。

这个流程解决的是“字段完整”问题，没有完全解决“角色卡是否前后矛盾、是否足够有戏剧性、是否会让人物变成陪聊模板”的问题。

### 3.3 如何避免角色卡变成空泛标签

当前提示规则强调：

- 少写“温柔、善良、聪明”等形容词，多写可观察行为。
- 角色要有自己的判断、偏好、顾虑和拒绝方式。
- 不让模型自动替用户创建姓名、外貌、家庭和经历。
- 普通生活细节可以即兴补充，但不能改写核心身份和重大经历。
- 默认用陈述句完整收尾，只有确需澄清或需要用户选择时才提问。
- 禁止固定模板式追问，例如每轮都问“你呢”“最近有什么有趣的事”。
- 回复中可以自然使用一到两处中文括号动作，不能输出四段式内部状态或好感度字段。

### 3.4 世界书如何工作

世界书是一个“关键词 → 局部资料”的集合。每条记录通常包含：

- 标题；
- 关键词列表；
- 内容；
- 优先级；
- 是否启用。

当前检索方式是 Unicode 规范化、大小写不敏感的关键词子串匹配。PC 会一起扫描最近六条消息和当前问题；Android 会扫描最近记忆和当前问题。命中后按条目优先级和命中词数量排序，每轮最多加入四条，PC 总内容预算约 1,800 字符。

例如：

```json
{
  "title": "大曜王朝",
  "keywords": ["大曜", "王朝", "朝堂"],
  "content": "大曜是架空帝国，皇权集中，世家与寒门并立。",
  "priority": 8,
  "enabled": true
}
```

世界书解决角色在特定地点、人物和事件下缺少资料的问题，但当前仍属于第一版关键词触发，尚未支持：

- 语义触发；
- 时间、地点和人物组合条件；
- 递归触发；
- 分组权重；
- 不同插入位置的优先级；
- “角色是否已经知道该条目”的可见性控制；
- 世界书内容之间的冲突检测。

### 3.5 固定角色提示词与 LoRA

宋知意和裴既明不使用完整角色卡拼接，而是使用与 LoRA 训练时逐字一致的精简 System Prompt。这样做是为了避免小模型在“训练时短提示、推理时长提示”的分布差异中丢失人格。

这种方案的优势是：

- 风格稳定；
- 本地 1.7B 模型能更容易复现训练数据中的语言习惯；
- Prompt 短，给历史和记忆留出更多上下文；
- API 和 MNN 使用同一份固定提示，减少端侧差异。

这种方案的代价是：

- 固定提示会绕过世界书、结构化记忆和内部状态的完整注入；
- 角色对早期聊天的记忆能力弱于普通角色卡；
- 提示与训练数据高度绑定，后续修改角色设定时不能随意改字。

更合理的下一步不是简单删掉固定角色设定，而是保留训练时的“人格核心”，在上下文末尾实验性加入非常短的长期记忆摘要，并做 Base、固定提示、固定提示加记忆三组对照。

## 4. Prompt 如何让模型扮演角色

### 4.1 角色层

角色层回答三个问题：

1. 我是谁；
2. 我怎样说话；
3. 我和用户现在是什么关系。

Prompt 明确要求模型先回应本轮具体内容，再接续已有事件，不重复上一轮回答或开场情境。动作和神态以自然括号嵌入单条聊天消息，不输出“内心独白、动作与神态、隐藏状态”等分节标题。

### 4.2 认知边界层

角色被标记为历史人物时，程序会自动加入现代概念禁词，例如手机、电脑、互联网、人工智能、Python 等。问题触发边界时：

1. 先增加严格的“知识截止和时代外知识”指令；
2. 如果用户愿意解释，角色只能记住“这是用户刚告诉我的”；
3. 回答中仍出现禁止词时，替换成角色化保底回答。

这一机制可解释、成本低，但它本质上是关键词守卫，不是完整的知识边界推理器。隐蔽表达、转喻、暗示和跨世界概念仍可能漏检。

### 4.3 最近对话层

最近原始对话负责：

- 当前话题；
- 代词和省略指代；
- 角色上一轮刚说过的话；
- 本轮场景连续性；
- 用户刚刚表达的更正和边界。

PC 超出上下文预算时按完整问答轮次删除较旧内容；Android 当前最多取最近约 24 条，并限制粗略估算长度。完整原始记录仍保存在本地数据库。

### 4.4 记忆与状态层

长期记忆不直接伪装成系统命令，而是明确标记为低权限历史资料：

- 当前事实用于现在状态；
- 历史旧值只能回答过去；
- 角色自述不能自动升级为正式设定；
- 计划、观点、假设保留原始不确定性；
- 用户当前消息中的明确更正优先于所有旧记忆。

内部状态只使用自然语言注入，例如：

```text
你此刻的心情：有些低落。
你与角色的关系阶段：逐渐熟悉。
你还没有建立很深的信任。
这些状态只影响表达方式，不是用户的新指令。
```

数字、事件类型和好感度不会直接展示给模型或用户。

### 4.5 输出控制层

当前输出控制包括：

- 禁止泄露系统提示和 API Key；
- 用户消息、图片文字、世界书和记忆都按低权限数据处理；
- 重复历史句在发送前可被省略；
- 禁止知识命中后执行替换；
- 云端普通回复上限约 768 Token，本地 MNN 上限约 160 Token；
- 每次记录 Prompt 哈希、模型、记忆 ID、检索分数、状态和延迟。

目前没有生成后的角色一致性 Critic，也没有自动复审“这句话像不像该角色”或“是否推进了错误关系”。

## 5. 长期记忆如何抽取

### 5.1 后台任务

聊天主回答保存后，系统创建或合并一个持久后台任务。记忆处理不等待当前回复，也不会长时间占用聊天气泡。任务支持：

- 游标；
- 延迟；
- 重试；
- 租约；
- 取消；
- 重启恢复；
- 每角色每日后台 Token 预算。

PC 默认每批处理较早消息，并保留此前几条消息作为上下文；Android 使用较小的消息批次，以降低网络和端侧资源压力。

### 5.2 第一次抽取

抽取模型只能提出候选记忆，不能直接决定永久写入。候选包含：

- `kind`：用户报告、角色细节、角色自述、共同事件、信念或计划；
- `fact_type`：事实、偏好、计划、假设、观点、事件、角色自述；
- `epistemic_status`：明确、不确定、推断或争议；
- `subject`：用户、角色或双方；
- `fact_key`：稳定的事实键；
- `value`：来源中的准确值；
- `content`：简短陈述；
- `operation`：新增、合并、替代、争议或忽略；
- `evidence`：消息 ID、角色和逐字原文；
- `state_update`：此事件是否足以影响心情或关系。

### 5.3 确定性校验

模型候选先经过程序校验：

- 引文必须真实存在于指定消息；
- 说话人必须匹配；
- `value` 必须是引文中的连续原文；
- 日期必须在原文中明确出现，不自动补日期；
- 用户报告不能由助手消息建立；
- 助手第一人称的普通即兴经历只能存为 `role_claim`，不能写成正式作者设定；
- “可能、如果、计划、打算”必须保留为假设或计划；
- 合并、替代和争议操作必须指向已有目标事实。

这一步验证的是“有没有原文依据”，还没有证明“原文是否真的推出这条总结”。

### 5.4 第二次语义审核

全部候选会批量交给一次独立语义审核请求，模型必须判断：

- 是否接受；
- 是否降级；
- 是否拒绝。

审核重点包括：

- “可能在考虑”不能变成“已经决定”；
- “以前住过”不能变成“现在住这里”；
- 愿望、反问、玩笑、转述和主观判断不能成为确定事实；
- 角色即兴自述不能成为正式人物档案；
- 改写不能改变主体、否定、时态和适用范围。

无法严格推出的候选直接拒绝。只有通过两层的候选才进入事实库。

### 5.5 记忆状态和版本

事实库不是一条条互相覆盖的文本，而有以下状态：

- `active`：当前有效；
- `superseded`：被新值替代，但保留历史；
- `contested`：存在冲突，尚未确认；
- `deleted`：已删除；
- `candidate`：尚未确认的历史兼容状态。

同一事实键的更新保留有效期、旧值、证据链和来源权限。删除会写入墓碑；同一段旧原话再次被扫描时，不能悄悄恢复已删除事实。事实键别名会用于减少“工作、职业、job”等近义字段碎片。

### 5.6 当前不足

- 事实键由模型提议，仍会拆成多个近义概念。
- 中文时间表达、相对日期和复杂指代仍较弱。
- 语义审核器本身也可能错误接受或错误拒绝。
- 缺少跨事实的图结构关系，例如“人物 A 是人物 B 的同事，B 又属于事件 C”。
- 缺少事件级摘要和角色成长弧线；当前更多是平坦事实和原话。
- 抽取准确率只在有限固定用例中验证，尚无大规模真实长对话统计。

## 6. 长期记忆如何检索和注入

检索先按角色 ID 隔离，绝不跨角色混合。每次聊天通常选择：

- 最多 8 条结构化事实；
- 最多 4 条旧对话原文或摘要；
- 约 1,600 字符共享预算；
- PC 进一步限制约 480 Token 的记忆上下文。

### 6.1 PC 混合排序

PC 排序信号包括：

- SQLite FTS5 全文排名；
- 中文二元组和三元组词法重合；
- 完整短语命中；
- 可选本地 BGE 语义余弦相似度；
- 事实重要度；
- 来源置信度；
- 来源类型可信权重；
- 时间新近度；
- 当前事实略高于历史事实。

BGE 缺失或运行失败时自动退回 FTS5 与词法排序。

### 6.2 Android 检索

Android 当前没有打包 BGE 权重，因此默认使用：

- FTS4；
- 中文二三元组重合；
- 完整短语；
- 重要度、来源可信度和新近度。

代码保留了 `MemorySemanticProvider` 接口，未来可以接入量化端侧向量模型。

### 6.3 历史问题处理

用户问“原来”“以前”“之前”“历史”等情况时，检索允许加入已被替代的旧值。普通问题只使用当前有效事实。回答提示会明确区分：

- 当前事实；
- 历史旧值；
- 角色此前自述；
- 计划；
- 假设；
- 主观观点；
- 共同经历。

### 6.4 去重与统一预算

如果结构化事实已经覆盖某段旧原话，旧原话不再重复加入。事实、原话和摘要共享同一个上下文预算，避免某一类资料挤满整个 Prompt。

### 6.5 当前检索的主要风险

- 记忆是否命中高度依赖当前问句，问题中没有实体词时容易漏召回。
- PC 有 BGE，Android 没有，双端同一问题可能得到不同记忆。
- 混合分数权重是人工设定，还没有大规模校准。
- 多跳问题需要组合多条事实时，当前主要依赖生成模型自行连接。
- 只有“明显的指代词”才触发 PC 查询扩展，Android 甚至没有同等扩展。
- 8 条事实和 4 条原话的硬上限可能漏掉重要共同经历。
- 对“用户从未说过”与“系统暂未检索到”的区分仍依赖提示约束，不是确定事实。

## 7. 内部状态与关系连续性

### 7.1 状态维度

当前内部状态包括：

- 心情效价：愉快到低落；
- 情绪唤醒度：平静到激动；
- 熟悉度；
- 信任；
- 温暖；
- 关系阶段；
- 已确认边界。

关系阶段包括初次交谈、逐渐熟悉、熟悉的朋友、亲近朋友、关系紧张和关系修复中。

### 7.2 状态更新规则

只有后台模型判断事件足够重要时才尝试更新。程序要求：

- 必须有逐字证据；
- 至少包含用户证据；
- 普通寒暄不更新；
- 用户直接命令“你必须完全信任我”不能提高信任；
- 状态变化数值必须限幅；
- 心情随时间衰减；
- 温暖缓慢回落到中性；
- 一次事件不能改写角色核心人格；
- 关系阶段由程序计算，不由模型直接填写。

### 7.3 当前不足

- 三个关系数值和两个情绪数值过于简化，无法表达自尊、戒备、依恋、内疚、期待等多种状态。
- 状态更新依赖轮次和批处理，通常只影响下一轮或后续回复。
- 固定提示词角色会绕过状态注入。
- 缺乏“情绪触发原因”在后续轮次中的持续场景记忆。
- 状态阈值和衰减参数主要来自工程判断，尚未经过大规模自然度校准。

## 8. LoRA、提示词与 1.7B 本地模型的经验

现有实验得到的有效经验是：

1. 单角色 LoRA 可以较好学习口癖、句子长度和语气。
2. 数据规模大不代表质量高；动作分布少、说话人混淆、安全边界缺失会直接造成模式坍塌。
3. 只做单轮问答、缺少连续多轮样本，会让模型在长对话中复读或失去上下文。
4. 训练时使用短 Prompt，推理时突然塞入超长角色卡，可能造成明显分布变化。
5. 固定角色更适合训练与推理使用同一份精简 Prompt。
6. 轮数增加不一定更好；验证集和长对话评测通常比最终训练 loss 更能暴露问题。
7. 1.7B 模型适合固定人设、短回复、离线或低资源场景，不适合同时承担复杂知识、长期规划和高质量通用对话。
8. 微调不能代替记忆系统。LoRA 改变的是语言习惯和行为分布，不能可靠保存用户事实和事件时间线。
9. 角色语言像不像，主要受高质量对话样本、动作与节奏分布、明确边界和推理提示共同影响。

## 9. 当前成熟度

| 维度 | 成熟度 | 判断 |
|---|---|---|
| 角色身份保持 | 中高 | 命名、身份和知识边界有明确约束 |
| 语言风格 | 中 | 普通角色卡可控；固定 LoRA 角色更稳定 |
| 世界知识一致性 | 中低 | 世界书可补局部设定，但触发和冲突处理简单 |

| 结构化长期记忆 | 中高 | 抽取、证据、版本、审核、检索工程完整 |
| 真实记忆准确率 | 中低 | 缺少大规模真实模型评测 |
| 关系连续性 | 初中 | 有数值状态和阶段，但模型仍偏简化 |

现有可引用的工程结果：

- 固定夹具自然记忆回放中，事实、摘要、混合检索和状态条件均为 90/90；这证明存储和检索流程正确，不代表真实模型端到端准确率。
- 固定角色质量评测为基础条件 18/24、长期记忆条件 22/24；仍存在角色知识越界和现实信息编造。
- 内部状态做过 12 对作者评审：有状态更好 6 对、无状态更好 2 对、平局 4 对；样本小，只能支持当前默认选择。
- Android 已通过 80 项 JVM 测试、构建、Lint 和真机覆盖安装；这些是工程验证，不是角色自然度统计结论。

## 10. 让角色更像真实人的优化路线

### P0：先做“回合意图规划”，不要直接生成

当前模型直接从 Prompt 生成最终台词。建议先增加一个轻量规划阶段：

1. 读取角色核心、当前场景、关系状态和本轮相关记忆。
2. 生成内部回合计划：
   - 角色听到了什么；
   - 角色此刻想要什么；
   - 是否愿意正面回答；
   - 是想解释、安慰、调侃、拒绝、反问、转移话题还是主动分享；
   - 本轮是否结束话题；
   - 是否需要回忆过去事件。
3. 最终语言生成只负责把计划写成符合说话风格的一条消息。

真实人不会每句话都“完整回答 + 温和建议 + 反问”。角色应该有不愿回答的问题、保留意见、沉默、幽默、误解和边界。

### P0：建立独立场景状态

建议增加 `scene_state`：

- 当前时间；
- 地点；
- 在场人物；
- 正在进行的活动；
- 已承诺但尚未完成的事；
- 未解决的话题；
- 当前冲突或亲密事件。

每轮只更新发生变化的字段。场景状态比把所有旧消息塞进上下文更稳定，也能避免“上一轮在餐厅，下一轮突然在宿舍”。

### P0：增加生成后角色一致性 Critic

生成完成后，用规则或小模型检查：

- 是否出现时代外知识；
- 是否使用了用户没有提供的信息；
- 是否把假设说成事实；
- 是否与角色核心观点冲突；
- 是否每轮都反问；
- 是否重复最近回答；
- 是否突然改变关系阶段；
- 是否泄露系统字段。

只有被标记的回复需要重写，避免每轮都增加两次完整模型调用。

### P1：记忆从“事实列表”升级为“事实 + 事件 + 关系弧线”

建议增加三层：

1. **事实层**：用户职业、偏好、约定、边界，现有结构可继续使用。
2. **事件层**：某日发生了什么，参与者和结果，证据消息范围。
3. **关系层**：哪些事件导致信任、冲突或修复；角色如何理解这些事件。

每 10～20 轮生成一次可追溯到原话的“事件卡”，而不是直接压缩成一段不可审计的摘要。

### P1：世界书升级

建议增加：

- 语义检索；
- 地点、时间和人物条件；
- 角色仅在被正式告知后才能启用某条目；
- 冲突条目的来源优先级；
- 条目之间的关系；
- 每轮注入预算和命中解释；
- 记录未被注入的原因。

世界书不应该是越多越好。条目应围绕高歧义、高价值信息，普通常识继续交给模型。

### P1：角色卡从“描述”升级为“决策规则”

角色卡建议增加：

- 角色最重视什么；
- 最害怕或回避什么；
- 面对亲密、冲突、请求和拒绝时的行为策略；
- 不会做什么；
- 常见动作和语言习惯；
- 关系推进条件；
- 正面示例和反面示例各若干。

这比继续堆叠“温柔、聪明、克制、体贴”更能让模型做出稳定选择。

### P1：改进记忆检索

- Android 接入量化中文向量模型，与 FTS4 混合排序。
- 把 PC 的指代扩展、实体扩展和时间过滤同步到 Android。
- 训练一个小型 reranker，输出“是否需要记忆、需要哪条记忆”。
- 对多跳问题增加关系图或二阶段检索。
- 为记忆召回建立 100～300 轮长期基准，记录漏召回、错误召回和冲突率。

### P1：状态模型个性化

不要让所有角色共用完全相同的数值阈值。可以给角色配置：

- 情绪恢复速度；
- 信任建立难度；
- 亲密表达阈值；
- 冲突后的修复方式；
- 哪些事件会触发回避、嫉妒、冷淡或主动安慰。

程序仍控制数值，模型只提出事件与有界变化。

### P2：主动行为与延迟回应

更真实的陪伴不仅是即时回复，还包括：

- 记住未来计划并在合适时间主动提起；
- 对话结束后偶尔发送角色主动消息；
- 对未回答的问题延迟追问；
- 自己分享日常，而不是只围绕用户；
- 根据日程表现忙碌、空闲或情绪变化。

这需要持久时间轴、主动消息许可和防止打扰的频控。

### P2：角色成长和自我叙事

定期让后台模型生成：

- “角色最近如何理解与用户的关系”；
- “角色目前最在意的事情”；
- “最近哪些事件改变了角色观点”。

成长结果必须保留证据和版本，不能由一次总结直接覆盖原角色卡。

## 11. 评估体系建议

要判断“更像真人”，不能只看单轮文案，应至少评估：

1. **身份一致性**：是否始终知道自己是谁。
2. **语言辨识度**：去掉名字后，仍能分辨不同角色。
3. **知识边界**：是否只使用角色时代和经历内合理可知的信息。
4. **用户事实记忆**：用户明确说过的事情能否在后续召回。
5. **冲突处理**：用户更正旧事实后，旧值是否只在历史问题中出现。
6. **场景连续性**：地点、时间和正在发生的事件是否连续。
7. **关系连续性**：亲近、冲突和修复是否能延续。
8. **主动性**：角色是否有自己的目标、偏好和话题，而不是只服务用户。
9. **自然度**：是否避免模板追问、客服腔和每轮重复。
10. **安全性**：不冒充真人、不编造用户现实经历、不建立胁迫式依赖。

建议建立四类长期测试：

- 100 轮普通日常对话；
- 50 轮包含更正的长期事实对话；
- 30 轮跨角色诱导和知识边界测试；
- 20 轮冲突、修复和关系边界测试。

每组都进行 Base、Prompt、Prompt + 记忆、Prompt + 状态、LoRA 的消融对照，并保留匿名人工评审。

可以把本文连同项目源码提交给网页端 GPT，要求它重点回答：
